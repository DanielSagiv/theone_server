# Joint Event / Merge Events – Reformulated Requirements

Reformulated from client requirements for clarity. Use this table to drive tasks later.

| # | Area / Feature | Clear requirement (rephrased) | Notes / Open questions |
|---|----------------|--------------------------------|------------------------|
| 1 | **Who can be in a Joint Event** | Allow **joint events** (shared experiences) for: (a) individual members, and (b) groups – where a **group rep** can include both members and non‑members. | Confirm: is there any limit on number of members / non‑members per group? |
| 2 | **Joint event flag** | Any COE (experience) that includes **joint events** must be clearly **flagged as "Joint Event"** in the system (data + UI). | Likely a boolean flag on the COE or event level. Need to decide where exactly: per COE, per event, or both. |
| 3 | **Statuses where joint is allowed** | Joint events are only allowed when the COE is in **`request`** or **`proposal`** status. | When COE moves to `experience` (paid), joint-setup is frozen; only revisions via "revised proposal" flow. |
| 4 | **Editing an existing proposal to add/change joint events** | If a **proposal already exists**, the admin must be able to **edit that proposal** to add / change joint events. The new version is still treated as the **same proposal**, now including joint‑event details. | Need to define how we version proposals (v1, v2…) and what history we keep. |
| 5 | **Flagging changed events** | When a proposal is edited (to add or modify a joint event), the **changed events** must be **clearly marked** in the proposal (both in admin UI and member UI). | E.g. tag as "Updated", "New joint event", "Removed" etc. |
| 6 | **Experiences that already exist (paid)** | If there is already an **experience** (member has paid deposit or full), and admin edits the proposal to include a joint event, the system must send a **revised proposal** that includes **only the changed events and the price differences**. | Clarify: revised proposal is an **add‑on** to existing experience, not a replacement of everything. |
| 7 | **Who receives revised proposals** | For a joint event, **all members in the joint event** receive the **new / edited proposal** that reflects the joint configuration (events + prices). | Need exact rules for group reps vs individual members: who approves vs who only pays. |
| 8 | **Payment deadline for joint events** | For all **joint events**, **each member** must pay **100% of their share** of the joint event price **within < 48 hours** of the new proposal. | Clarify: is it always exactly 48h from send time? Different timezone handling? |
| 9 | **Existing 20% deposits and new joint event price** | If a member has **already paid 20% deposit** on a previous proposal, and now receives a joint‑event proposal, then for the **joint event part only**, the new amount due should be **reduced by the 20% deposit already paid**. | We need a **clear payment breakdown**: old deposit, new joint event gross price, deposit credit, net amount due. |
| 10 | **Non-joint events payment flexibility** | For events in the proposal that are **not joint events**, the **admin can manually determine** the payment amount (e.g. 20% vs 100%, custom). | Need UI/control for admin to set payment rules per event / per proposal. |
| 11 | **Content of a new/edited proposal** | A new or edited proposal should include only: (a) the **updated list of experiences/events**, and (b) the **updated prices**. | Confirm whether we re‑send all events in the proposal or only show a "diff" section. |
| 12 | **Updating the experience upon payment** | Once the member completes payment for the proposal (including joint event), the linked **experience must be fully updated** to reflect: events, prices, and payment status. | This includes updating any joint flags, seat allocations, and balances. |
| 13 | **Scenario: joint proposal not paid in time** | If the **new joint-event proposal is not paid within 48h** by **any** required member, that proposal is **expired**. We also **must send reminders** during this 48h window. | Need exact reminder schedule: e.g. at send, +24h, +36h? And what happens if some pay and some don’t? |
| 14 | **Scenario: member has previous paid proposal** | If a member already has a **previous proposal that became an experience** (deposit or full paid), and the new joint proposal expires, the member should **fall back to that previous experience** by default. | No extra action required by member; their original booking remains valid. |
| 15 | **Scenario: member had unpaid previous proposal** | If the member had a proposal that was **never paid** (no deposit, no full payment), and the new joint proposal expires, the **old unpaid proposal also expires by default**. The admin may then either **re-use** the old proposal or **create a new one** based on it. | Need admin tools to "revive" / clone old proposals and adjust them. |
| 16 | **Ghost table / zone reservations** | Support **reserving a zone** (section) using a **"ghost table"**: a placeholder seat/table that is not shown to the customer. In the UI and documents, the customer sees only the **section name**, never the exact table. | We need a way to flag certain seats as "ghost" and adjust client UI and docs to hide the table code/ID. |
| 17 | **Joint event availability by status** | Joint events should only be editable / attachable while COE is in `request` or `proposal`. Once status moves to `experience` or beyond (e.g. `paid`), joint events can only be managed via new **revised proposals**, not by editing the existing experience directly. | This is essentially a guardrail: enforce at API level. |
