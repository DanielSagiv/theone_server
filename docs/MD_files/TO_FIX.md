### COE request flow – risk scan (logic, security, data integrity)

| Area / Component | Risk type | What I see as the risk | Where it comes from (files / patterns) | Potential impact | Suggested mitigation (no code, just direction) |
| --- | --- | --- | --- | --- | --- |
| Text‑based bot parsing (`Client ID`, `Request COE ID`) | **Logic + Data integrity** | Critical fields are extracted from free‑text message lines using regex (`Client ID: …`, `Request COE ID: …`). Any formatting change, translation, or missing line can make the server mis‑detect client or fail to link `request_coe_id`. | `COECreateForm.js` (building message parts), `botPreferenceService.js` (regex for IDs), `botService.js` / `botToolHandlers.js` (using `request_coe_id`, `client_id`) | Wrong client attached to a COE, duplicate COEs instead of upgrading the existing request, hard‑to‑trace bugs when text format changes. | Move these critical identifiers into structured tool payloads / explicit fields instead of relying on text parsing; keep the text lines only as display copies. Add server‑side validation that `request_coe_id` and `client_id` exist and belong to the current conversation/user. |
| In‑memory `coeSelectionStore` | **Logic + Data integrity (session)** | Selection is stored only in a local JS singleton; it’s cleared in some places and not persisted per COE or per user. If user navigates in a non‑standard order or app is restarted, local selection and what the server thinks was selected can diverge. | `src/state/coeSelectionStore.js`, `COECreateForm.js`, `coe-event-selection.js`, `event-seats.js` | User might see a summary of events that doesn’t match what actually got sent to the bot / server, especially if multiple COEs are created in one session. | Tie selection to a specific COE draft / conversation ID in the store, or persist to backend when “Done” is pressed so server is the single source of truth. Ensure the store is cleared/updated only when a COE is actually submitted or cancelled. |
| Flow A upgrade vs. new COE creation | **Data integrity** | Upgrade from `request` → `draft` depends entirely on `request_coe_id` being correctly extracted and passed. If it’s missing or malformed, `handleCreateCOEDraft` falls back to `createCOE`, re‑introducing the “two COEs (request + draft)” issue for those cases. | `botPreferenceService.js` (extract), `botService.js` (passes into tool), `botToolHandlers.js` (`handleCreateCOEDraft`) | Duplicate COEs for a single user request, inconsistent status reporting, confusion in admin dashboards. | Add explicit server‑side guard: if a bot tool call claims to be “build from request” but cannot find / validate the `request_coe_id`, either reject with a clear error or log and do not create a second COE silently. |
| Heavy console logging of PII and full COE data | **Security** | Many logs include full client objects, emails, COE contents, events, and seats with `[COE_CREATION_FULL_DEBUG]` / `[COEDetail]` dumps. In production logs this is sensitive. | `COECreateForm.js`, `coe-detail.js`, `botToolHandlers.js`, `coes.js` and others with large `console.log` blocks | If logs are shipped to external services or accessed by support, they expose user PII, booking details, and spending/budget info. | Gate detailed logs behind `NODE_ENV === 'development'` or a feature flag; in production, log only IDs and high‑level status, not full objects or personal data. |
| Authorization for COE detail access | **Security** | Access checks for `/coes/my/:id` look at several roles, but logic is complex; bugs here could accidentally allow a user to see a COE where they’re not client/admin/runner/participant, especially if ObjectId vs string comparison is mishandled. | `server/routes/coes.js` (`GET /v1/coes/my/:id`, `COE.findOne` access filters, `coeExists` checks) | Information disclosure: a user may see another client’s experience details or pricing if checks drift from the intended access rules. | Add targeted tests for all roles (client, admin, runner, unrelated user) for various COE states; centralize the “has access to COE” check in a single helper reused across all COE routes. |
| Event/seat consistency in populated COEs | **Data integrity** | You already filter `selected_seats` to only seats whose `event_id` still exists in `events`, but this is done in a few code paths; if any future endpoint returns COE data without that filter, old or mismatched seats can leak through. | `server/routes/coes.js` (`filterSelectedSeatsByEvents` usage on `/coes/my`, `/coes/client/:clientId`), `coeService.filterSelectedSeatsByEvents` | UI can show seats for events that are no longer part of the COE, leading to wrong totals and “no seats selected” errors in some flows. | Enforce `filterSelectedSeatsByEvents` inside the service/model layer whenever COEs are loaded, not just in specific routes; consider a small integrity check before saving COE updates as well. |
| Date/time handling for event search in selection step | **Logic** | Mobile builds `start_date` / `end_date` as `YYYY-MM-DDT00:00:00Z` and `...23:59:59Z` without considering user timezone. Combined with server overlap logic, this can drop or include events off by one day, depending on region. | `coe-event-selection.js` (building query), `botToolHandlers.js` event overlap logic comments | Users around timezone boundaries may not see expected events or see slightly out‑of‑range events, which then impact COE contents. | Normalize both client and server date handling around a clear timezone strategy (e.g., always store and query in UTC, but convert user‑entered dates to UTC using their timezone). Add tests for edge dates (midnight, DST) for COE event search. |
| Client‑side validation only for some constraints | **Logic / mild security** | Certain rules (e.g., “one event per venue type per day”) are enforced in the mobile UI only. If another client is added later (web, script) and it doesn’t enforce these rules, the backend will accept states that the app UI would never generate. | `coe-event-selection.js` (UI enforcement, comment explicitly says it doesn’t modify COE payload logic yet) | Inconsistent behavior across clients and potential “impossible” COE states if another consumer calls the APIs directly. | Mirror critical business rules in backend validation (e.g., in `handleCreateCOEDraft` or `coeService`), not just in the mobile UI. |
